# RELEASE v0.13.0 — Playground: one container inits and serves

**Status:** ready — static + binary checks green offline; clean-machine compose run needs a tag build (user)
**Theme:** *`docker compose up -d` is a populated playground: one GrepRUM container migrates, seeds demo data and serves — no one-shot containers.*

## Why

The quickstart stack ran two one-shot containers around the gateway: `migrate` (always) and `seed`
(`--profile demo` run). That is three GrepRUM containers per demo stack — three image pulls, three pods
in Kubernetes terms — and a newcomer had to know which extra command produces demo data
(ADR [0053](../docs/adr/0053-playground-inits-and-serves-in-one-process.md)).

## Scope

1. **`greprum playground`** — init and serve in one process: the `migrate --wait` retry loop, then a
   guarded demo seed, then the same serve path as `serve`. Flags: `--config`, `--wait`, `--demo-data`,
   `--events` (30 000), `--days` (7), `--seed` (7), `--site`.
2. **Seeding is guarded twice.** It writes only the `demo` site and only when the loaded config defines
   it (a production config via `GREPRUM_CONFIG` gets none), and only when the site has no events in the
   generated window (fixed SQL, bound site, capped window — a restarted container never duplicates rows;
   append-mode tables reject `DELETE`, ADR 0029).
3. **Compose drops both one-shots.** `docker compose up -d` starts four services (`greptime`, `greprum`
   playground, `prometheus`, `grafana`); no `restart: "no"`, no `condition: service_completed_successfully`.
   `make demo` / `make demo-local` are a plain `up`.
4. **Production path unchanged:** `serve` stays the image default and the recommendation for own configs;
   explicit init is one ad-hoc command (`docker compose run --rm greprum migrate …`).
5. This supersedes the v0.12 compose wiring; the AC0.12.1/2 tests were updated to the playground flow
   (their criteria are enforced in their new shape — zero-edit compose, deterministic demo data, plain
   `make demo`).
